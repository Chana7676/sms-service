# שירות שליחת SMS לעובדים

שירות HTTP ששולח SMS לעובדי הארגון דרך ספק SMS, שומר כל הודעה במסד נתונים ומאפשר לעקוב אחרי הסטטוס שלה.
האפיון המלא שלפיו נבנה הקוד: [SPEC.md](SPEC.md).

## הרצה

דרישה מוקדמת: [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0). לא נדרשת התקנה של מסד נתונים או שירות חיצוני –
קובץ SQLite נוצר אוטומטית בהפעלה הראשונה.

```bash
dotnet run --project src/SmsService.Api
```

ואז לפתוח: **http://localhost:5000/swagger** (או F5 ב-Visual Studio על `SmsService.sln`).
קובץ ה-DB (`src/SmsService.Api/sms.db`) נוצר עם עובדים לדוגמה.

בדיקות:
```bash
dotnet test
```

ממשק (אופציונלי, דורש [Node.js](https://nodejs.org)) – בטרמינל נוסף, כשה-API רץ:
```bash
cd client
npm install
npm run dev
```
ואז לפתוח: **http://localhost:5173**

דוגמה לשליחה (טלפון נוכחי של עובדת קיימת):
```json
POST /messages
{
  "to": { "firstName": "שרה", "lastName": "כהן", "address": "הנשיא 5, ירושלים", "phone": "0522222223" },
  "body": "תזכורת: ישיבת צוות מחר ב-9:00"
}
```

## מה בניתי

| Endpoint | מה עושה |
|----------|---------|
| `POST /messages` | בודק קלט, מוודא שהטלפון הוא הטלפון הנוכחי של העובד, שומר הודעה `Pending`, מכניס לתור ומחזיר מיד `202 { id }` |
| `GET /messages/{id}` | ההודעה והסטטוס שלה (`Pending` / `Sent` / `Failed`) |
| `GET /messages?status=&page=&pageSize=` | רשימה מהחדשה לישנה, עם סינון לפי סטטוס ועמודים |
| `GET /employees` | לממשק: עובד אחד בכל שורה עם הטלפון הנוכחי |

**ממשק (React):** עמוד עובדים – חיפוש, בחירה (כולל "סמן הכל"), כתיבת הודעה ושליחה לכל הנבחרים.
עמוד הודעות – טבלה עם סינון לפי סטטוס, שמתרעננת כל 3 שניות.

**איך נשלחת הודעה:**
```
POST ──▶ DB: Pending ──▶ תור בזיכרון ──▶ SmsWorker ──▶ ספק
                                            ▲
                       כל דקה: Pending שנכשלו ┘   (3 ניסיונות בסך הכל – ראשון ועוד 2 חוזרים – ואז Failed)
```

**טכנולוגיות:** ASP.NET Core 8 Web API, EF Core + SQLite, xUnit (58 בדיקות: יחידה + אינטגרציה מול השרת בזיכרון),
React + TypeScript (Vite).

**מבנה:** `Controllers` (HTTP בלבד) · `Services` (לוגיקה) · `Providers` (הספק, מאחורי ממשק) · `Workers` (שליחה ברקע) · `Data` (DB) · `client` (ממשק).

## הנחות יסוד

1. **`to` הוא מופע של עובד: שם פרטי, שם משפחה, כתובת וטלפון.** לפי המשימה עובד מזוהה לפי שם + משפחה + כתובת, ולכל עובד
   כמה מופעים עם טלפונים שונים. כך ההודעה מקושרת תמיד לעובד מסוים (גם כשהטלפון משותף), הולידציה על הטלפון היא על הקלט,
   ולא נחשף מזהה פנימי (מגבלת האבטחה). הודעה אחת = נמען אחד, כמו "מחזיר מזהה הודעה" בדרישה.
2. **כמה רשומות לאותו עובד = כפילות; הרשומה העדכנית (לפי `CreatedAt`, ובשוויון – `Id` גבוה) היא הטלפון הנוכחי.**
   הרשומות הישנות נשמרות כפי שהגיעו, והטלפון הנוכחי מחושב בשאילתה.
3. **שולחים רק לטלפון הנוכחי של עובד קיים.** אחרת `422`. מונע שליחה למספר זר או ישן.
4. **טלפון משותף לכמה עובדים – הודעה נפרדת לכל עובד**, כי לכל אחד סטטוס משלו.
5. **מספרים ישראליים בלבד** (`05XXXXXXXX`). מקפים ורווחים מתקבלים ומנורמלים.
6. **הכתובת מגיעה ממקור מובנה** (בחירה מרשימה / שירות כתובות), ולכן מספיקה השוואה מדויקת.
7. **העובדים מוגדרים בקוד לצורך הדגמה** (`EmployeeSeedData`), כולל בכוונה כל מקרה קצה. במציאות – סנכרון ממערכת משאבי האנוש.
8. **ספק ה-SMS המדומה לא התקבל**, ולכן מימשתי ספק מדומה בקוד (`FakeSmsProvider`) שמדמה השהיה ושגיאות (10%).
   הנחתי שהספק מקבל הודעה ומחזיר "קיבלתי" או שגיאה. כל הקוד שתלוי בספק נמצא מאחורי `ISmsProvider`,
   כך שחיבור לספק האמיתי = מחלקה אחת + שורת רישום אחת.
9. **`Sent` = הספק קיבל את ההודעה**, לא שהיא הגיעה לטלפון. מעקב מסירה לא נדרש ולא מומש.
10. **מופע אחד של השרת.**

## החלטות עיקריות

- **ה-POST לא מחכה לספק (`202 Accepted`).** הוא שומר, מכניס לתור וחוזר מיד. כך ספק איטי או שנפל לא מעכב את המשתמש,
  והמבנה תואם את הדרישה: POST מחזיר מזהה, ו-GET נפרד מחזיר סטטוס. שגיאות קלט (`400`) ועובד/טלפון (`422`) חוזרות מיד.
- **תור בזיכרון (`Channel`) ולא MQ.** MQ דורש שרת נפרד, בניגוד ל"רץ בפקודה אחת", ולא נדרש בקנה המידה הזה.
  ההודעה נשמרת ב-DB **לפני** שהיא נכנסת לתור, כך שהפעלה מחדש לא מאבדת אותה: סבב הניסיון החוזר שולח אותה.
  הסתייגות: קריסה אחרי שהספק קיבל ולפני עדכון הסטטוס עלולה לגרום לשליחה כפולה – הסיכון והפתרון בחלק ב'.
- **ניסיון חוזר: כל דקה, 3 ניסיונות בסך הכל, עד 50 הודעות בסבב.** SMS בדרך כלל דחוף ותקלות ספק בדרך כלל קצרות – תשובה סופית
  תוך כ-2 דקות. ההגבלה לסבב מונעת הצפה של הספק כשהוא חוזר אחרי נפילה.
- **בלי polling לסטטוס מסירה.** שקלתי לשאול את הספק שוב ושוב "נמסר?", אבל בקנה מידה זה עשרות אלפי בקשות מיותרות,
  והנחה נוספת על ה-API של הספק. הדרך הנכונה למעקב מסירה היא Webhook מהספק.
- **טבלת סטטוסים עם מפתח זר + `enum` בקוד** – ה-DB עצמו מונע סטטוס לא חוקי, והקוד בטוח-טיפוסים.
- **שומרים את הטלפון גם בהודעה** – כדי לדעת לאיזה מספר נשלח בפועל גם אם נתוני העובד ישתנו.
- **ולידציה עם DataAnnotations** – הכללים פשוטים; ספרייה כמו FluentValidation הייתה מיותרת.
- **SQLite + EF Core** – קובץ אחד בלי התקנה. **`EnsureCreated`** במקום Migrations.
- **אורך הודעה עד 335 תווים** – SMS בעברית (UCS-2) הוא 70 תווים, ו-67 לכל חלק בהודעה מפוצלת; 335 = 5 חלקים.

## מה בחרתי לא לעשות, ולמה

| לא עשיתי | למה |
|----------|-----|
| שליחה לכמה עובדים בבקשה אחת | הדרישה: הודעה אחת ומזהה אחד. הממשק שולח בקשה לכל עובד שנבחר |
| מעקב מסירה לטלפון (`Delivered`) | דורש Webhook או polling מול הספק; לא נדרש |
| Idempotency-Key (הגנה מלחיצה כפולה בשרת) | לא נדרש. מתואר בחלק ב' |
| MQ אמיתי (RabbitMQ וכו') | דורש תשתית נוספת; תור בזיכרון + DB מספיקים כאן |
| ממשק מלא (עמודים, מיון, חלון אישור, פרטי הודעה) | הממשק אופציונלי – נבנה בגרסה מינימלית |
| אימות משתמשים, Deploy, Docker | לא נדרש |

## מה הייתי מוסיפה עם עוד זמן

- **`POST /messages/batch`** – מערך עובדים, שמירה בפעולה אחת והכנסה לתור; ובהמשך שליחה לפי קריטריון ("כל העובדים").
- **בממשק** – עמודים בטבלת ההודעות, סינון לפי תאריך / עובד, וסימון טלפון משותף בטבלת העובדים.
- **ניסיון חוזר עם מרווח שגדל** (דקה, 5, 15) ו-jitter, ומעבר לספק שני כשספק נופל לזמן ארוך.
- **"שלח שוב"** ידני להודעות `Failed`.
- **Webhook מהספק** לסטטוס מסירה, ו-timeout להודעות שלא אושרו.
- **Idempotency-Key** – קוד ייחודי לכל פעולת שליחה, כדי שבקשה כפולה לא תיצור הודעה שנייה.
- **טלפונים לא תקינים בנתונים** – דוח איכות נתונים למשאבי אנוש, והתראה בממשק לפני שליחה.
- **היסטוריית הודעות לעובד**, סינון לפי תאריך / עובד, מספרים בינלאומיים (E.164).

  ולעיתים שיניתי כיוון אחרי בדיקה (למשל: `to` כמופע עובד, רק הטלפון העדכני, ויתור על polling לטובת תור וניסיון חוזר).

  טלפון בלבד מול מופע עובד).
